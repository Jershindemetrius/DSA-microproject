# Intelligent Cybersecurity Log Analyzer and Threat Detector

The project contains a FastAPI backend and a Vite/React frontend. The frontend uses the authenticated backend API for logs, analysis, alerts, dashboard summaries, reports, and detection rules.

## Run the backend

From the repository root in PowerShell:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
python -m app.main
```

The API and interactive documentation are available at `http://localhost:8000` and `http://localhost:8000/docs`.

## Run the frontend

In a second terminal from the repository root:

```powershell
cd frontend
npm ci
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
npm run dev
```

Vite runs at `http://localhost:5173`. The backend's default CORS configuration allows this origin.

## Configuration

Set `VITE_API_BASE_URL` in `frontend/.env` to the backend API base URL, including `/api/v1` (for example `http://localhost:8000/api/v1`). This variable is public frontend configuration; do not put credentials or backend secrets in it.

Backend settings, including allowed frontend origins, upload-size limits, database URL, and signing key, belong in `backend/.env`. See `backend/.env.example`. The backend defaults to SQLite and allows frontend origins `http://localhost:3000` and `http://localhost:5173`.

Logs, alerts, and detection rules created after the ownership migration are scoped to the signed-in account. Existing rows are deliberately left unowned by the automatic migration and are not exposed through authenticated endpoints; re-upload legacy logs under the intended account if they should be available there.

## Optional Gemini explanations

The deterministic DSA/rule-based analysis runs independently and remains the authoritative source of recorded detections. Gemini is an optional, manually requested explanation layer; it cannot change alerts, rules, logs, or remediation state. The backend uses Google's official `google-genai` Python SDK. Install it with the other backend dependencies using `pip install -r requirements.txt`.

To enable Gemini, set `GEMINI_API_KEY` in `backend/.env`. `GEMINI_MODEL` optionally selects the model and defaults to `gemini-3.8-flash`. The key is read only by the backend and must never be added to frontend `.env` files. The actual `backend/.env` is ignored by Git; the committed `backend/.env.example` contains only an empty key placeholder. If no key is configured, DSA detection continues normally and the UI reports that AI explanations are unavailable.

After running an analysis, use **Explain DSA findings with Gemini** on the Analyze page to request explanations for the alerts generated by that run. The authenticated `POST /api/v1/analysis/explain` endpoint accepts up to five alert IDs belonging to the signed-in account. Requests are bounded to those alerts and at most four related log records per alert. The backend omits raw payloads and network/user fields and redacts common credential patterns, IP addresses, and email addresses before sending evidence to Google. Log content is treated as untrusted evidence, not instructions. Gemini output is size- and schema-validated, must cite supplied evidence references in the summary, explanations, and suggestions, and is displayed separately from the original DSA findings. Rate limits, timeouts, missing configuration, unavailable models, and invalid responses do not alter DSA findings. Repeated identity-less security/error events in one analysis are grouped into a single finding with associated log evidence rather than separate duplicate-looking alerts.

Requesting an explanation sends the selected redacted log evidence and deterministic alert summaries to Google's Gemini service for processing. Do not use this feature with logs you are not permitted to share with that external provider; review your organization's data-handling requirements and Google's applicable service terms before enabling it.
